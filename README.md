# TTP-Study — Exact Methods for the Traveling Tournament Problem

Undergraduate research project (2023) comparing exact optimisation approaches for the
**Traveling Tournament Problem (TTP)**: building a double round-robin schedule for
`n` teams that minimises the total distance travelled, while limiting how many
consecutive home or away games each team plays.

Four solvers are implemented and benchmarked on the same set of random instances:

| Method | Idea | Stack |
|---|---|---|
| **MIP** | Compact mixed-integer formulation of the full schedule | Gurobi |
| **CP** | Constraint-programming model of each team's opponent/venue sequence | OR-Tools CP-SAT |
| **Column generation, MIP pricing** | Master problem over team *tours*; new tours generated by a MIP subproblem | Gurobi |
| **Column generation, CP pricing** | Same master problem; tours generated by a CP-SAT subproblem | Gurobi + OR-Tools |

## Problem

- `n` teams (even), `2(n − 1)` time slots; every pair of teams meets twice, once at each venue.
- Each team plays exactly one game per slot.
- No team may play more than `U = 3` consecutive home or away games (`L = 1`).
- Travel cost: each team starts at home, follows its sequence of venues, and returns home
  at the end. The objective is the sum of all teams' travel distances.

## Column-generation approach

The decomposition is implemented in [`ttp_master.py`](ttp_master.py) (`TTPMaster`).

- **Patterns (columns).** A pattern for team `t` is its *tour*: the venue it is at in every
  slot. Its cost is the distance travelled along that tour.
- **Master problem (LP relaxation).** Choose exactly one pattern per team so that, in every
  slot, each team is either away (according to its own pattern) or hosting exactly one
  visitor (according to the other teams' patterns).
- **Pricing.** The dual values of the master problem are passed to a *satellite* subproblem
  that searches, for each team, for a feasible tour with negative reduced cost. Two
  interchangeable implementations are provided:
  - [`ColGenIP_IP/MIP_col_gen.py`](ColGenIP_IP/MIP_col_gen.py) — `MIPPatternGenerator` (Gurobi)
  - [`ColGenIP_CP/cpgenerator.py`](ColGenIP_CP/cpgenerator.py) — `CPPatternGenerator` (CP-SAT)

  Both encode each pattern as an integer hash and add no-good constraints, so a tour
  that has already been generated is never generated again.
- **Initial columns and infeasibility.** Initial columns come from feasibility-only calls to
  the subproblem. If the restricted master is infeasible, more columns are added
  heuristically.
- **Integer solution.** When column generation converges or times out, a binary version of
  the master is solved over all generated columns to obtain an integer schedule. This is
  *not* a full branch-and-price, so the resulting schedule is not guaranteed to be optimal.

The baseline compact models are [`TTP_MILP.py`](TTP_MILP.py) (MIP) and
[`cpsolver.py`](cpsolver.py) (CP).

## Benchmark

Random instances are generated by placing `n` teams uniformly on a 100 × 100 grid and
taking rounded Euclidean distances ([`inst_gen/`](inst_gen)). There are 5 instances for each
`n ∈ {4, 6, 8, 10}`, stored in [`instancesTTP/N_*/`](instancesTTP). Each solver had a
**2-hour time limit** per instance.

Average best integer objective found (lower is better). The numbers come from the CSVs in
[`instancesTTP/results_*/`](instancesTTP):

| n | MIP | CP | Col. gen. + CP pricing | Col. gen. + MIP pricing |
|---|---|---|---|---|
| 4 (5 inst.) | **780** — optimal, ~2 s | **780** — optimal, ~1 s | 800 — LP converged, ~3 min | — (crashed) |
| 6 (5 inst.) | **1,697** — time limit | 1,708 — time limit | no integer sol. | no integer sol. |
| 8 (5 inst.) | 4,193 — time limit | **3,949** — time limit | no integer sol. | no integer sol. |
| 10 (1 inst.) | 6,011 — time limit | **5,248** — time limit | — | no integer sol. |

**Takeaways**
- For `n = 4`, both compact models prove optimality in seconds.
- For `n ≥ 6`, nothing finished within 2 hours. MIP finds slightly better schedules at
  `n = 6`, and CP-SAT is clearly better from `n = 8` on.
- Column generation with CP pricing converges for `n = 4`. Its integer schedules are on
  average about 3% above the optimum (up to 7% on one instance), which shows the cost of
  not branching. For larger `n` the pricing
  problem becomes the bottleneck and no integer schedule was found.
- The MIP-pricing variant failed on several runs (see [`errors_log.txt`](errors_log.txt)).
  The `n = 10` row reflects a partial run.

## Repository structure

```
ttp_master.py          # Column-generation master problem (TTPMaster)
TTP_MILP.py            # Compact MIP model
cpsolver.py            # Compact CP-SAT model
ColGenIP_IP/           # MIP pricing subproblem (+ earlier standalone solver)
ColGenIP_CP/           # CP pricing subproblem (+ earlier standalone solver)
CP_CP/, Old things/    # Earlier experiments, kept for reference
inst_gen/              # Instance generation, loading and result writing
instancesTTP/          # Benchmark instances and results per method
parallelizer.py        # Runs every (method, instance) pair in parallel processes
parallel_solve.py      # Worker: solves a single instance with a given method
sequential.py          # Sequential version of the benchmark
```

## Running

Requirements: Python 3, [`gurobipy`](https://pypi.org/project/gurobipy/) (with a
Gurobi licence; a free academic licence works) and
[`ortools`](https://pypi.org/project/ortools/).

```bash
pip install gurobipy ortools
```

Run from the repository root, since paths are resolved relative to the working directory:

```bash
python parallelizer.py
```

Set `POBLATE = True` in `parallelizer.py` to generate new instances, and adjust `N`,
`methods` and `TIMEOUT` there to choose what to run. Results are written to
`instancesTTP/results_<method>/results_N_<n>.csv`.
